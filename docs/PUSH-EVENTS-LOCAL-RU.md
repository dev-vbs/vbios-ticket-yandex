# Push-уведомления о событиях услуг SHM

Сначала включите уведомления на тестовом устройстве в кабинете и убедитесь, что тестовое уведомление приходит. Шаблоны ниже выполняются в SHM через транспорт `local` в контексте владельца услуги. Они отправляют уведомление всем его подписанным устройствам.

Поля `title` и `body` задают заголовок и текст сообщения. Их можно изменить под свой сервис. При нажатии на уведомление откроется относительный путь из `url`. Браузер и операционная система определяют внешний вид и количество видимых строк. Одно и то же значение `tag` может заменять предыдущее уведомление на устройстве.

## Создайте шаблоны

В административной панели SHM создайте отдельный шаблон для каждого сообщения. Укажите приведённый ID и скопируйте только содержимое соответствующего блока.

**ID `Push_Service_Create_LOCAL`**

```text
{{ result = user.srv('Push').send(
    title = 'Услуга оплачена'
    body = 'Услуга создана. Откройте личный кабинет, чтобы проверить её состояние.'
    url = '/services'
    tag = 'service-created'
) }}
```

**ID `Push_Service_Activate_LOCAL`**

```text
{{ result = user.srv('Push').send(
    title = 'Услуга активирована'
    body = 'Проверьте состояние услуги и настройки подключения в личном кабинете.'
    url = '/services'
    tag = 'service-activated'
) }}
```

**ID `Push_Service_Prolongate_LOCAL`**

```text
{{ result = user.srv('Push').send(
    title = 'Услуга продлена'
    body = 'Новый срок действия можно посмотреть в личном кабинете.'
    url = '/services'
    tag = 'service-renewed'
) }}
```

**ID `Push_Service_Block_LOCAL`**

```text
{{ result = user.srv('Push').send(

    url = '/services'
    tag = 'service-blocked'
) }}
```

**ID `Push_Service_No_Money_LOCAL`**

```text

**ID `Push_Service_Changed_LOCAL`**

```

## Привяжите события

В разделе событий SHM добавьте отдельное правило для каждого необходимого уведомления. Существующие правила Remnawave сохраните. В каждом правиле укажите `kind` равным `UserService`, `server_gid` равным `0`, а `name` и `template_id` возьмите из таблицы.

| Событие `name` | ID шаблона | Когда используется |
| --- | --- | --- |
| `CREATE` | `Push_Service_Create_LOCAL` | Создание услуги после успешной оплаты |
| `ACTIVATE` | `Push_Service_Activate_LOCAL` | Активация услуги |
| `PROLONGATE` | `Push_Service_Prolongate_LOCAL` | Продление услуги |
| `BLOCK` | `Push_Service_Block_LOCAL` | Приостановка услуги |
| `NOT_ENOUGH_MONEY` | `Push_Service_No_Money_LOCAL` | Недостаточно средств для создаваемой услуги |
| `CHANGED` | `Push_Service_Changed_LOCAL` | Изменились параметры услуги |
| `CHANGED_TARIFF` | `Push_Service_Changed_Tariff_LOCAL` | Изменился тариф услуги |
| `REMOVE` | `Push_Service_Remove_LOCAL` | Услуга удалена |

Пример `settings` для правила `PROLONGATE`. Замените `remna` на фактическую категорию основной услуги в вашей установке.

```json
{
  "category": "remna",
  "transport": "local",
  "template_id": "Push_Service_Prolongate_LOCAL"
}
```

Для остальных правил поменяйте `name` и `template_id` по таблице. Если поля в панели отображаются отдельно, задайте те же значения в них. Не используйте пример категории, пока не проверите категорию своей услуги. Добавляйте правила отдельно от действующих правил создания и управления Remnawave.

В SHM также есть внутренние переходы `BLOCK FORCE` и `ACTIVATE FORCE`, но они не входят в список обычных событий `UserService` и не добавляются этим комплектом. Если ваша установка действительно создаёт для них отдельные правила, используйте отдельные шаблоны с теми же текстами, что для `BLOCK` и `ACTIVATE`, и проверьте это на тестовой услуге.

## Проверьте на тестовом пользователе

1. Войдите под тестовым пользователем, включите уведомления и отправьте тест из кабинета.
2. Создайте нужное событие на тестовой услуге и проверьте задание в очереди SHM. Получателем является владелец услуги, а не администратор, который создал правило.
3. Проверьте результат задания и журнал `docker compose -f docker-compose.yml logs --tail=50 push`. Повторное выполнение события или задания может повторно отправить уведомление.

Эти правила реагируют на события SHM. Они не создают напоминание за несколько дней до окончания, уведомления об ответах поддержки или новых устройствах. Для них нужны отдельные триггеры и проверка защиты от повторов. Результат отправки `sent` означает, что браузерная push-служба приняла уведомление, а доставку на экран следует проверить на устройстве.
