# Yandex Cloud: приватные картинки тикетов vBios

Инструкция для подготовленного модуля ticket-yandex-update. Нужен Yandex Object Storage (S3), не Яндекс Диск. Названия пунктов консоли могут немного отличаться. Реальное облако и ваши ключи здесь не проверялись.

## 1. Подготовьте облако

1. Откройте https://console.yandex.cloud/ и войдите в аккаунт.
2. Подключите активный платёжный аккаунт к облаку. Хранение, операции и передача данных могут тарифицироваться.
3. В выбранном облаке создайте отдельный каталог, например `vbios-tickets`. Отдельный каталог позволяет выдать права только на ресурсы тикетов, не затрагивая остальные бакеты.
4. Выберите этот каталог перед следующими шагами.

## 2. Создайте сервисный аккаунт

1. Откройте сервис IAM / раздел «Сервисные аккаунты» выбранного каталога.
2. Нажмите «Создать сервисный аккаунт».
3. Имя: `vbios-ticket-storage`.
4. Для простого варианта назначьте ему роль `storage.editor` **на отдельный каталог vbios-tickets**. Она предоставляет чтение, запись и удаление объектов. Не назначайте общую роль editor/admin на всё облако.
5. Сохраните аккаунт.

Роль на каталог распространяется на ресурсы этого каталога: держите здесь только бакет тикетов. Если требуется строгое ограничение одним бакетом в общем каталоге, настройте bucket policy с правами конкретного сервисного аккаунта по документации Yandex вместо широкого назначения. Не добавляйте публичный доступ или универсальный запрет, который заблокирует сервисный аккаунт.

## 3. Создайте бакет

1. В каталоге `vbios-tickets` откройте Object Storage.
2. Нажмите «Создать бакет».
3. Задайте уникальное имя латиницей, например `vbios-ticket-images-ваш-уникальный-суффикс`. Не копируйте кириллицу из этого примера в настоящее имя. Удобный вариант имени: `vbios-ticket-images-2026-48291` — только если оно свободно.
4. Выберите стандартное хранилище для картинок, которые часто открываются в тикетах.
5. При наличии поля максимального размера задайте разумный предел, например 5 ГБ для начала. Это не заменяет бюджетные уведомления и не ограничивает все расходы.
6. Доступ на чтение объектов: ограниченный/приватный.
7. Доступ к списку объектов: ограниченный/приватный.
8. Доступ к настройкам: ограниченный/приватный.
9. Создайте бакет.

Не включайте публичный сайт, публичное чтение и CDN для этой задачи. Все обращения выполняет SHM с серверными ключами. CORS на бакете для данной реализации не требуется.

Не настраивайте автоматическое удаление всех объектов через 7/30 дней без согласованной политики хранения: это удалит картинки действующих тикетов. Управление сиротами/удалением в подготовленном модуле автоматизировано не полностью.

## 4. Получите статический ключ

1. Откройте сервисный аккаунт `vbios-ticket-storage`.
2. Выберите «Создать новый ключ» → «Создать статический ключ доступа» (S3-совместимый).
3. Добавьте описание `vBios ticket images`.
4. Сохраните два значения: идентификатор ключа доступа и секретный ключ. Секрет может быть показан только при создании.

Нужен именно статический S3-ключ. Не IAM-токен, не OAuth-токен, не API-ключ ИИ, не ключ от аккаунта Яндекс.

Не присылайте ключи в чат, не вставляйте в клиентский config.js и не публикуйте в GitHub. Если секрет уже опубликован, создайте новый ключ, обновите сервер и удалите старый.

## 5. Настройте сервер SHM

На сервере откройте существующий файл:

```bash
cd /opt/shm
nano .env
```

Добавьте, сохранив остальные переменные:

```dotenv
TICKET_S3_ACCESS_KEY=ВАШ_ACCESS_KEY_ID
TICKET_S3_SECRET_KEY=ВАШ_SECRET_ACCESS_KEY
VBIOS_SOURCE_DIR=/opt/vbios-ticket-yandex/server
VBIOS_CLIENT_SOURCE_DIR=/opt/vbios-ticket-yandex/client
```

Последние два пути нужны при сборке с предоставленным override. В каталоге server должны быть Dockerfile и app/, в client — Dockerfile и package.json. Если распаковали в другое место, задайте настоящие пути.

```bash
chmod 600 /opt/shm/.env
```

Переменные .env сами по себе не передаются в контейнеры. В core и spool должны быть:

```yaml
environment:
  TICKET_S3_ACCESS_KEY: "${TICKET_S3_ACCESS_KEY:-}"
  TICKET_S3_SECRET_KEY: "${TICKET_S3_SECRET_KEY:-}"
```

В предоставленном `compose.ticket-storage.yml` эти поля уже есть. Не создавайте второй core/spool в одном YAML-файле.

## 6. Подготовьте БД и код

Если ещё не установлены подготовленные изменения, распакуйте новые серверные и клиентские исходники. Скопируйте SQL `ticket-object-storage.sql` из комплекта в `/opt/shm/` и примените:

```bash
cd /opt/shm
docker compose exec -T mysql sh -c \
  'MYSQL_PWD="$MYSQL_PASSWORD" exec mysql -u"$MYSQL_USER" "$MYSQL_DATABASE"' \
  < ticket-object-storage.sql
```

Требуется установленная схема тикетов, включая ticket_media. Если нет права CREATE, выполните SQL под администратором БД. Таблица ticket_media_objects дополнительная; старые картинки не удаляются. Эта SQL не создаёт ticket_ai_jobs: таблица ИИ относится к другому модулю.

Скопируйте compose.ticket-storage.yml в /opt/shm и соберите:

```bash
cd /opt/shm
docker compose -f docker-compose.yml -f compose.ticket-storage.yml config --quiet
docker compose -f docker-compose.yml -f compose.ticket-storage.yml build core api client
docker compose -f docker-compose.yml -f compose.ticket-storage.yml \
  up -d --no-deps --force-recreate core spool api client
```

Выполняйте последующие команды управления этими локальными образами с обоими -f. Основной Compose без override может вернуть старые образы. При обновлении переменных окружения нужен `up --force-recreate`, простого `restart` недостаточно.

Если код уже установлен и менялись только ключи, повторно собирать не нужно, но core/spool пересоздайте с теми же Compose-файлами.

## 7. Настройте config.ticket

В административном интерфейсе SHM откройте конфигурацию с ключом ticket. Добавьте или исправьте только вложенный объект storage:

```json
"storage": {
  "provider": "yandex",
  "bucket": "vbios-ticket-images-2026-48291"
}
```

Замените имя на реально созданный бакет. Остальные поля ticket — id группы, telegram_profile, ai — сохраните. Ключи доступа в конфигурацию вставлять не обязательно: они читаются из окружения core/spool.

Для созданного модуля endpoint фиксирован: https://storage.yandexcloud.net, регион ru-central1. Поля endpoint/region в клиенте не нужны. Не указывайте в bucket URL, каталог tickets/ или заглушку «ИМЯ_ВАШЕГО_ПРИВАТНОГО_БАКЕТА» — только имя бакета.

Если вы используете временный шаблон для настройки, после создания ticket можно обновить storage так:

```tt
{{ IF config.ticket }}
  {{ r = user.srv('config').id('ticket').set_json('value', {
    storage = {
      provider = 'yandex'
      bucket = 'ВАШЕ_РЕАЛЬНОЕ_ИМЯ_БАКЕТА'
    }
  }) }}
{{ END }}
```

Выполнять под администратором. Предварительно сохраните текущую конфигурацию. Затем проверьте значение через админку.

## 8. Лимит загрузки Nginx

Во внешнем Nginx в server-блоке кабинета/API:

```nginx
client_max_body_size 10m;
```

Примените:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Лимит нужен на каждом промежуточном прокси: файл 5 МиБ при base64 увеличивается примерно до 6,7 МиБ. В обновлённых исходниках API лимит уже увеличен, в клиентском Nginx он был задан ранее.

## 9. Проверка без раскрытия ключей

```bash
cd /opt/shm
docker compose -f docker-compose.yml -f compose.ticket-storage.yml exec core sh -lc '
  test -n "$TICKET_S3_ACCESS_KEY" && echo "Access key передан" || echo "Access key отсутствует"
  test -n "$TICKET_S3_SECRET_KEY" && echo "Secret key передан" || echo "Secret key отсутствует"
  test -f /app/lib/Core/TicketStorage.pm && echo "Модуль установлен"
'
```

Не используйте для диагностики `env`, `printenv` или полный `docker compose config` с публикацией вывода: в них могут находиться секреты.

В кабинете:

1. Создайте тестовый тикет с небольшой PNG/JPEG.
2. Убедитесь, что отправка завершилась без ошибки, картинка открывается и скачивается.
3. Перезагрузите страницу: картинка должна остаться доступной.
4. В Yandex Object Storage откройте бакет: появится ключ tickets/USER_ID/СЛУЧАЙНОЕ_ИМЯ.png.
5. Прямой анонимный URL объекта не обязан открываться — приватность ожидаема.
6. Проверьте старое вложение из БД: оно должно остаться доступным.

Проверка метаданных в MySQL:

```sql
SELECT m.id,m.name,m.mime_type,m.size,
       OCTET_LENGTH(m.data) AS db_bytes,o.bucket,o.object_key
FROM ticket_media m
LEFT JOIN ticket_media_objects o ON o.media_id=m.id
ORDER BY m.id DESC LIMIT 10;
```

Для нового облачного изображения db_bytes=0, заполнены bucket и object_key. Старые BLOB не переносятся автоматически.

## 10. Ошибки и причины

| Ошибка | Что сделать |
|---|---|
| Credentials are missing | Проверить окружение core/spool, затем пересоздать контейнеры |
| HTTP 403 от Object Storage | Проверить статический ключ, роль storage.editor/политику бакета и время сервера |
| HTTP 404 от Object Storage | Проверить настоящее имя бакета и наличие объекта |
| HTTP 413 от Nginx | Увеличить client_max_body_size на всех прокси |
| ticket_media_objects отсутствует | Применить SQL до использования нового модуля |
| Новая картинка не открывается, старые работают | Проверить ключи, bucket/object_key и новый серверный модуль |
| Картинка не видна только в кабинете | Обновить клиент вместе с сервером: скачивание использует новый JSON/base64-контракт |
| Картинка не приходит в тему Telegram | В этом обновлении Telegram отправляет текст тикета, не вложения |

Для проверки времени: `timedatectl status`. Для проверки сети: `curl -I --connect-timeout 10 https://storage.yandexcloud.net`. Ответ 403/404 на корень endpoint сам по себе нормален: проверяется соединение, не доступ к вашему объекту.

Логи:

```bash
docker compose -f docker-compose.yml -f compose.ticket-storage.yml logs --tail=100 core spool
```

## 11. Расходы, хранение и резервные копии

Настройте бюджет и уведомления расходов в Billing. Они помогают контролю, но не являются гарантированной мгновенной остановкой расходов. Контролируйте объём, операции и исходящий трафик.

После перехода картинки находятся вне MySQL. Одного shm_backup.sql уже недостаточно для полного восстановления: сохраняйте бакет/объекты и таблицы метаданных вместе. При необходимости включите версионирование, учитывая стоимость хранения старых версий и порядок удаления.

Не удаляйте бакет или ключи, пока существуют облачные вложения. Удаление строки в БД в подготовленной реализации не удаляет объект автоматически. Неотправленная форма может оставить неиспользуемое вложение. Периодическую очистку нужно организовать отдельно с проверкой привязок и периодом ожидания.

Скриншоты могут содержать персональные данные. Выберите срок хранения, круг сотрудников с доступом и порядок удаления. ИИ в текущей интеграции не читает изображения; облачная загрузка сама по себе не добавляет распознавание картинок.
